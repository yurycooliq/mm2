# Owner console

The console is a separate Python standard-library process. It samples the private engine state once per second and stores secondary history in its own SQLite volume. Opening more browsers does not add engine samplers. Engine decisions, durable commands and the exchange emulator do not depend on the dashboard or this database.

The dashboard labels the selected execution profile: offline demo (`emulator`), public simulation, read-only shadow, trading or both. It displays engine/API/feed readiness, book receive/exchange ages, source and lane faults, limits, receipts, finite engine journal capacity and sampled history. Trading displays separate real collateral, reservations, positions and orders, with account reconciliation and user-stream status. Both also displays the independent simulated account and companion phase. Last sampled values must be interpreted with the connection/readiness indicators; an unreconciled real balance is unknown. Public shadow has no real account balance.

Paper cash belongs to a retained multi-market portfolio; available cash is labelled for the current market. Old positions retain their original market identity, and synthetic merge/demo resolution assumptions remain simulation-only. Final net PnL remains unavailable. The live lane separately exposes a conservative realized result from confirmed owned returns minus conservative purchase basis; POL gas is accounted separately without an invented exchange rate. The chart shows sampled simulated available cash. A selected profile cannot be changed with Resume: choose it at process startup using `scripts/start.py --mode simulation|trading|both|shadow|demo` or `scripts/start.ps1 -Mode <mode>`. Every profile starts paused; unconfigured trading templates refuse activation. See [OPERATIONS.md](OPERATIONS.md).

## Runtime configuration

| Variable | Meaning/default |
| --- | --- |
| `MM2_ENGINE_URL` | Private HTTP(S) engine origin; Compose uses `http://engine:8088`. No credentials, path, query or fragment. |
| `MM2_ENGINE_API_TOKEN` | Required private engine token, 32–256 printable ASCII characters. Never sent to the browser. |
| `MM2_CONSOLE_TOKEN` | Separate owner token with the same length bound. Must differ from the engine token. |
| `MM2_ALLOWED_ORIGINS` | Comma-separated exact console origins. Local defaults: `http://127.0.0.1:8080,http://localhost:8080`. |
| `MM2_CONSOLE_HOST` / `MM2_CONSOLE_PORT` | Default `0.0.0.0` / `8080`; bind/publish locally as configured by Compose. |
| `MM2_CONSOLE_STATE_DIR` | Default `/data`, the console's own persistent volume. |
| `MM2_CONSOLE_STATIC_DIR` | Default `/app/dashboard`, compiled frontend files. |
| `MM2_TELEGRAM_BOT_TOKEN` / `MM2_TELEGRAM_OWNER_ID` | Both absent disables Telegram completely; both supplied enables the owner bot and Telegram-only HTTP authentication. |
| `MM2_TELEGRAM_ONLY` | `true` disables token login even before bot credentials are provisioned; AWS sets it permanently. `false` cannot downgrade a configured bot. |
| `MM2_TRUSTED_PROXY_HEADER` | Default `false`; AWS alone enables the reviewed private Caddy rate-limit boundary below. |
| `MM2_MINIAPP_URL` | Optional HTTPS console URL, whose origin must also be explicitly allowlisted. |

If the console owner token is empty, startup generates a random token once and stores it in the private state directory as `console-owner-token`, with restrictive file permissions. Obtain it from that private runtime file; it is never written to logs. Do not place credentials in source, URLs or screenshots. Keep the engine token server-side, including behind a reverse proxy. Configure the public HTTPS console origin explicitly and preserve the matching Host header. Arbitrary API/provider destinations are not accepted.

The host entry point is `python -B -m mm2_console`, with `PYTHONPATH=apps/console`, the runtime environment above and a built dashboard. `npm ci`, `npm test` and `npm run build` run in `apps/dashboard`; the Docker build supplies its static `dist` directory.

## Authentication and control

With Telegram configured, the owner opens the Mini App without entering a console token. The server verifies the signed owner launch before issuing a random HttpOnly cookie. Local token login is disabled and unauthorized API requests return a neutral 404. Without Telegram configuration, local login accepts the separate console owner token. Sessions expire after one hour and are held in a bounded in-memory set of 32 sessions. Logout revokes them. Every unsafe HTTP request requires an exact allowlisted Origin and matching Host; cookies use SameSite Strict locally. Telegram HTTPS sessions use Secure/SameSite None to support the Mini App frame. Session cookies and credentials are omitted from access logs. The public bootstrap HTML contains no account data.

The console validates Telegram's signed `initData` using the documented HMAC scheme, restricts the signed user ID to the complete numeric owner ID, rejects ambiguous fields and replayed initData, and checks a five-minute TTL with at most five seconds of future clock skew. The same launch may reload with its own bound, valid cookie; another client cannot reuse it. A reload after the launch data expires requires reopening the Mini App. The frontend validates the Telegram launch before using an existing cookie and never falls back to token login after a rejected Telegram identity. See [Telegram Mini App validation](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app). The official SDK loads only for a Telegram launch with a bounded timeout. WebView cookie restrictions depend on the client; actual owner embedding remains a separate acceptance check. Use the hidden credential entry described in [TELEGRAM_SETUP.md](TELEGRAM_SETUP.md).

A rejected Telegram launch revokes any submitted owner session: switching Telegram accounts cannot keep access through a previous owner's cookie. Foreign-origin requests are rejected before touching sessions. AWS's console port is unpublished and reachable through isolated private service networks. Only there, the explicit trusted-proxy flag permits a single valid `X-MM2-Client-IP` from a private non-loopback socket peer for rate-limit buckets. Caddy overwrites this header with its actual remote socket IP; the header never grants authentication. `X-Forwarded-For` is never trusted. Keep DNS only/direct Caddy; a CDN or a public console port requires a separately reviewed proxy boundary.

Browser commands retain the original command ID, expected engine version and exact payload in origin-local `localStorage` **before** dispatch. A reload or closed/reopened Mini App restores an unresolved request. No token or cookie is stored there. An uncertain transport result, timeout, 5xx, mismatched/missing receipt, or 401/403/429 rejection keeps that identity. Reauthenticate or wait for the rate limit, then retry the original request. A matching durable receipt settles it; a definitive engine rejection such as a 409 also settles it and restores controls. Deleting browser storage loses that recovery record, so do not clear it to bypass an unknown outcome. Use one owner control surface at a time.

Pause/Resume/Kill/Reset and limits use the engine's bounded API with unchanged IDs and compare-and-swap versions. Kill, Reset and Resume with a real trading lane have explicit UI confirmation. Trading Resume remains disabled until the published live eligibility gate is ready. The UI labels success only after a matching receipt with a valid applied version and mode. An HTTP response or a button click alone is not a durable acknowledgement. A pending limits request displays its original values as well as its ID/version. Live and paper effects have independent durable journals; a UI receipt does not create cross-journal atomicity. Live risk settings remain part of the validated public trading profile; the existing limits form is not a complete editor for those settings.

The owner bot accepts private-chat `/start`, `/status`, `/stats`, `/active`, `/pause`, `/resume`, `/kill`, `/reset` and `/logs`, with sender and chat ID both matching the owner. Other users receive no response. The owner chat gets a Mini App menu and `/start` button. Status separates real/paper funds, marks stale or unreconciled balances unknown, reports lane health and finite journal capacity, and never labels collateral or a conservative loss bound as realized PnL. `/active` separates filled positions from working/uncertain orders. `/stats` sends statistics and a generated PNG deposit chart for the latest 24 hours, sampled once per minute. Deposit valuation uses cash plus complete positions at fresh best bids; missing prices, old markets or inconsistent cash/fill evidence create gaps rather than invented values. This estimate excludes depth and fees and is not realized PnL. Simulation stays explicitly virtual.

Controls require a fresh message and a fresh sampled engine publication. The bot persists command identity in SQLite before dispatch and keeps uncertain commands pending across restart; repeating the same command reconciles the same payload. Different controls are blocked while it is unresolved. Masked authentication 404 responses cannot clear a browser's unresolved command identity. Updates use bounded [Telegram long polling](https://core.telegram.org/bots/api#getupdates). Notifications use sampled engine fill counters/audit deltas, with a persisted baseline to avoid historical floods after restart. The cursor advances before sending because Telegram has no send idempotency key: a crash or unknown send result can omit a secondary message. Sampling gaps are logged. The retained engine ledger remains the execution record. Telegram outages and charts never add engine requests or block execution. Development tests use public fixtures/mock transports and send no external messages.

## API and bounds

| Console route | Behavior |
| --- | --- |
| `GET /healthz` | Process health; does not poll the engine. |
| `POST /api/auth/local` | `{token}` creates the owner cookie only when Telegram is not configured; otherwise 404. |
| `POST /api/auth/telegram` | `{init_data}` validates the signed owner launch. |
| `GET /api/state` | Cached `{state, observed_at_ms, connected, error, telemetry, execution}`; `execution` separates real/paper summaries and journal capacity. |
| `GET /api/history?limit=120` | Up to 120 secondary samples. |
| `GET /api/logs?limit=100` | Up to 100 secondary logs. |
| `POST /api/control` | Exact `{id, expected_version, action}` proxy. |
| `PUT /api/limits` | Exact `{id, expected_version, limits}` proxy. |
| `POST /api/logout` | Revoke the session. |

Authenticated reads use cached state or SQLite; they never make private engine requests. The single sampler's internal engine request has a 1.5-second transport timeout. No fresh sampler receipt for 3.5 seconds, an engine publication older than three seconds, or an invalid publication clock makes `connected=false` and disables dashboard controls. The last observed statistics remain visible with a stale/error label. An HTTP 200 from a stalled cached engine state does not establish freshness.

Ingress is bounded to 16 HTTP workers, a three-second socket read timeout, 16 KiB request bodies, 16 KiB accepted headers, 2 KiB paths, and bounded rate-limit tables. Authentication and commands have separate rate limits. Engine transport concurrency is four and response size is capped at 256 KiB; redirects are rejected and HTTPS certificate validation remains enabled. Static files are capped at 2 MiB and must resolve inside the compiled dashboard directory. Security headers include a restrictive Content Security Policy, no-store and nosniff.

SQLite retains at most 900 samples and 1,000 logs, with a 24-hour age policy on writes. A separate compact deposit table retains at most 10,080 minute points/seven days; `/stats` reads at most 1,440 points from the latest 24 hours. Profile/reset changes and collection gaps break chart lines. Each ordinary sample is capped at 64 KiB; log messages at 256 characters. Oversized state is projected into a marked bounded historical summary before storage; order/position/book detail may be omitted, while the current cached UI state is retained. Compaction and dropped writes are counted separately. The database page limit is 64 MiB; WAL/checkpoints are separately bounded by short transactions and configured checkpoint/journal limits. Storage failures drop **secondary** writes and increase visible counters. This database is not a replacement for the engine ledger. The state envelope reports history/log drops, history compaction, sampler overruns, publication lag and storage errors. Secondary health logs record profile, lane fault/readiness and journal-capacity transitions without serializing signed wire intents or credentials.

## Verification

Console tests cover authentication/CSRF/session replay and bounds, secret separation, single sampling, stale publications, retention/restart, transport identity/CAS, mocked Telegram receipt/pending recovery, real/paper summaries and bounded secondary history. Frontend checks cover persisted command identity, uncertain/rejected outcomes, receipt validation and exact limits. Current test/build results and their scope are maintained in [VALIDATION.md](VALIDATION.md).

Earlier fixture browser checks exercised all four controls, confirmation dialogs, limits, an uncertain command, reload, close/reopen, and a subsequent definitive 409. The original integrated demo console was authenticated against the local emulator with fake QA credentials; those screenshots are historical evidence, not validation of every later trading screen. Desktop/mobile concepts and integrated screenshots, plus the visual comparison ledger, are retained in `docs/design` and [DASHBOARD_DESIGN.md](DASHBOARD_DESIGN.md). Controlled mock checks do not establish actual venue execution, real funds, external Telegram delivery or profitability.
