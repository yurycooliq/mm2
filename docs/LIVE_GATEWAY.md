# Live gateway: implemented technical scope

`mm2-live` is a BUY-only, single-account execution service with a real Polymarket SDK transport and an injectable offline transport. It does not establish strategy profitability, grant funded authorization, or provide a complete portfolio closeout service. All development execution tests use an in-memory `Venue`; the signature test uses public fixture key `1`, with no network or account credentials.

The dependency is pinned to `polymarket_client_sdk_v2 = 0.7.0`. This implementation supports the SDK's Polygon CLOB V2 token order representation, its configured V2 exchange and collateral contracts, and signature types EOA, canonical proxy and canonical Safe. It rejects V3 positions, deposit-wallet EIP-1271, negative-risk markets, sells, merge and redemption. SDK support in this code must not be confused with the protocol currently deployed for a particular account/market. A fresh venue protocol check is required before signing and during account reconciliation. See the [official migration guide](https://docs.polymarket.com/migrate/clob-sdk-to-unified-sdk), the [official Rust repository](https://github.com/Polymarket/rs-clob-client-v2), and the [pinned crate API](https://docs.rs/polymarket_client_sdk_v2/0.7.0/polymarket_client_sdk_v2/).

## Public integration interface

```rust
LiveRuntime::start(settings: LiveSettings, state_dir: PathBuf)
    -> Result<LiveHandle, String>; // async; production SDK transport
LiveRuntime::start_with_venue(settings, state_dir, Arc<dyn Venue>)
    -> Result<LiveHandle, String>; // async; dependency injection for offline tests

handle.snapshot() -> Arc<LiveSnapshot>;
handle.subscribe() -> watch::Receiver<Arc<LiveSnapshot>>;
handle.resume_ready() -> bool;
handle.try_submit_quotes(Vec<LiveQuote>, timestamp_ms: u64) -> Result<(), String>;
handle.command(command_id: String, ControlAction) -> Result<LiveControlReceipt, String>; // async
handle.shutdown() -> Result<(), String>; // async
```

`try_submit_quotes` replaces the entire desired set in one coalescing watch slot. It performs bounded local validation and does not wait for signing, HTTP, console polling or disk. Supply a fresh timestamp and keep refreshing the desired set while it remains wanted. Empty sets are accepted while paused. Signing/posting happen in the executor; a late preparation result is discarded if its desired identity or freshness no longer matches. This is not a lossless queue of individual strategy decisions.

Each quote carries `slot`, `condition_id`, `market_slug`, decimal `token_id`, `outcome`, exact `price_micros` and `quantity_micros`, `window_start_ms`, `window_end_ms`, `tick_micros`, `min_order_micros`, approved maximum `fee_bps`, `protocol` and `neg_risk`. Currency/shares use six decimal micro units; products use twelve decimal pico units serialized as strings. SDK size precision requires quantity multiples of 10,000 micro shares. The gateway resolves venue condition/token/outcome identity, accepting state, end time, minimum, tick and V2 fee parameters before it signs. It rejects mismatches rather than silently changing price, quantity, token or market.

Approved markets are bounded exact condition IDs and/or the explicitly configured `btc-updown-5m-` family. Family quotes require an integer slug timestamp aligned to five minutes, the matching start timestamp and a 300-second interval. The SDK then verifies the actual condition, token pair, slug and end time. The prefix does not authorize arbitrary caller-supplied tokens.

Owner actions are `Pause`, `Resume`, `Kill`, `Reset`. Commands have a bounded durable ID. Repeating an ID with a different action is a conflict. Repeating the same ID returns its stored receipt and does not reapply the action. In particular, a historical Resume receipt can say `running` while the current recovered executor remains paused. The caller must display current snapshot phase separately from receipt phase and use a new owner command to resume after recovery. The parent engine retains its own durable CAS command contract; child IDs preserve that identity across the two journals.

## Credentials, readiness and order preparation

`LiveSettings` contains public addresses, deployment identity, risk policy, scheduling bounds and environment-variable names. It never contains key values. `owner_authorized` defaults to false. Production startup validates the explicit owner/funder/signer relationship and pinned deployment before it reads private environment values. EOA funder equals signer; proxy/Safe funders must match the SDK's canonical derivation. Supplied L2 API credentials are used directly; no API key creation/derivation, allowance transaction or automatic funding occurs.

Startup always recovers paused, preserving a killed latch. Active recovered orders become cancellation/reconciliation candidates. Readiness requires a connected authenticated user stream, a recent successful complete account reconciliation, heartbeat success, no foreign open order, no unresolved order outcome, and no fault. An owner Resume is rejected before these gates pass. Private stream disconnect durably pauses the executor and clears desired quotes; reconnect requires fresh reconciliation and a new Resume identity.

Preparation runs protocol, market and V2 token/fee metadata requests concurrently. Market and token metadata caches contain at most 64 entries each and expire after one second; a caller tick/minimum change bypasses the token cache. Immutable identity changes are rejected. The SDK's indefinitely cached `version()` is supplemented by a one-second public `/version` refresh using a pooled HTTPS client and compared with the signing client's version. An unsupported protocol is a visible preparation failure, not an automatic downgrade or version-changing resubmission.

V2 platform fees come from `/clob-markets/{condition}`'s `fd` parameters. Legacy V1 `fee_rate_bps` is not used. A taker-only fee is zero for these post-only maker orders. Otherwise the V2 price curve is converted upward to a conservative basis-point bound for reservation/accounting and must fit the caller's approved bound. The recorded gross purchase cost is conservative; it is not a confirmed settlement fee statement or PnL.

All orders are BUY and post-only. The SDK builds and signs GTC/GTD orders without submitting them. GTD is chosen where expiration satisfies its security buffer; the final minute uses GTC. This buffer is not a strategy-wide final-minute prohibition. Desired-quote expiration, source freshness and software cancellation still apply to GTC. The executor stops wanting orders one second before the configured market end; cancellation and fill delivery have finite network latency, so this does not prove that every order is terminal exactly at the deadline. The venue heartbeat provides an additional cancellation mechanism, and its actual selected-host behavior remains a canary gate.

## Durability, uncertainty and reservations

The signed V2 EIP-712 order hash is computed before any POST. Its validated quote, signed wire representation and possible-fill reservation are synchronously persisted before the network worker may submit. The SDK's combined build/sign/post helper is deliberately not used: it could rebuild an order identity on a protocol mismatch. A timeout or missing acknowledgement never causes a new submission of the same economic intent.

Post and cancel timeouts preserve `unknown_post`/`unknown_cancel` state and possible-fill reservations. Cancellation has dedicated worker capacity independent of a slow POST or preparation. A cancel acknowledgement only triggers an authoritative query; it does not release collateral. Recovery and runtime reconciliation use bounded open-order and trade pagination, per-order authenticated REST queries with at most eight concurrent active queries, balance/allowance and Data API positions. A complete query pass is applied as one account observation; a non-404 error or identity mismatch discards partial results. A missing order/404 plus an empty open list is insufficient proof that a timed-out submission never reached the venue. Such uncertainty remains reserved and blocks Resume until it can be resolved. Authenticated websocket messages trigger REST reconciliation; they do not directly free funds.

Per-order cumulative fills are monotonic. Terminal fill regression and fills that contradict an already terminal observation fault the service. A separate persisted position floor captures pre-existing account holdings before new effects and increases only from owned cumulative fill deltas. Observed Data API quantity is compared with this floor; it is never used as the accumulator for later fill deltas. This handles both ahead and lagging portfolio snapshots without counting an owned fill twice, and the floor survives pruning of terminal diagnostics. Old live ledgers missing that floor are rejected rather than guessed. The session cash bound does not replenish from a stale balance response. Open orders belonging to another executor are shown as foreign identities and prevent resumption. This implementation does not adopt or automatically cancel foreign orders.

Before read-only preparation, an optimistic zero-fee risk check skips impossible slots so they cannot starve an admissible hedge. Read-only preparation then normalizes the venue maker fee before capital admission. The final normalized risk check remains before any durable send intent or external order, so a conservative caller fee bound cannot accidentally prevent a valid hedge solely before its authoritative maker fee has been learned.

The ledger preserves one finite capital pool across markets. Admission applies budget, gross exposure, maximum order/market counts, independent possible Up/Down fills and per-market imbalance. Opposite open orders do not cancel each other's worst-case inventory. `daily_loss_micros` is labelled `conservative_gross_purchase_loss_bound`, and `pnl_available` is false: the current safety metric bounds today's gross purchase cost including the conservative fee estimate, rather than claiming realized daily PnL. Sale/redemption proceeds are not recycled automatically. Changing the public risk configuration on restart does not erase historical spend or reservations.

## Persistence and bounded diagnostics

The account directory is fenced by `live.lock`. Trading and both profiles must point to the same explicit account `live_state_dir`; their separate parent/paper directories do not create a new funded-account budget. Files are `live-identity.json` and `live-{starting_sequence:016}.jsonl`. The identity file is raw SHA-256 hex of the serialized public tuple `(host, owner, funder, signer, signature_type, chain_id, protocol, exchange, collateral)`. Policy/env reference names are not part of that account/deployment identity.

Each newline record contains `sequence`, `previous_hash`, `hash`, `reason` and the full ledger. The hash covers the canonical serialized tuple `(sequence, previous_hash, reason, ledger)`. Replay validates sequence/hash continuity, canonical segment names, bounded lines and semantic quote/position quantities. A partial record is a startup error; it is not silently truncated. Only an empty final segment with the next starting sequence is accepted as a pre-write rotation crash state.

Segments rotate at 8 MiB, with at most 256 retained segments and a configurable total capacity from 1 MiB to 1 GiB. Records are limited to 1 MiB. Rotation preserves the full chain and never deletes old records. New posts stop before consuming the journal's reserved cancellation headroom; eventual total exhaustion faults execution and stops heartbeat renewal. This is finite storage, not automatic compaction or indefinite unattended operation. Use the repository's locked backup/restore tools and alert before capacity exhaustion; never delete unresolved intents or reset the account ledger to recover capacity.

Current records are full checkpoints, so storage/latency per state-changing event grows with the bounded retained ledger. Identical account reconciliation, stable desired quotes, time pulses and heartbeat updates do not produce checkpoint writes. Frequent fills, replacements, cancellation retries and owner commands still consume capacity; selected-host throughput/capacity must be measured. Limits include 256 tracked orders/signed intents, 128 positions, 2,048 control receipts, 256 private events, 32 owner commands and one desired-quote watch slot. These quotas fail closed.

`LiveSnapshot` exposes current phase/readiness, account/stream/heartbeat evidence timestamps, collateral, allowance, exact reserve, conservative available cash, positions, unknown/active orders and faults. Telemetry includes all active orders plus at most 16 closed diagnostics, with total tracked/active counts. It also exposes `journal_bytes`, `journal_max_bytes`, durable sequence, quote coalescing count, preparation attempts/failures and a bounded `last_prepare_error`. Signed wire intents and secrets are excluded. Signed execution journals remain private account material and must not be copied into browser/UI logs.

Periodic immutable snapshots are published at up to 4 Hz; control/network/fault transitions may publish immediately. Snapshot copying is bounded but has nonzero cost. JSON/percentile/history formatting belongs outside the execution actor. Console availability, SQLite and Telegram are not prerequisites for quote expiry, cancellation or reconciliation. `both` uses a separate paper actor, ledger and bounded feed/control mirroring; secondary delay/fault never waits on the live actor's decision path.

## Remaining activation and capability gates

Offline tests verify command/recovery identity, durability-before-effect, lost acknowledgements, partial fills, cancellation uncertainty, cancel priority, stale/disconnected streams, independent possible-fill limits, semantic replay validation, unchanged-checkpoint suppression and primary/paper isolation. They do not verify actual maker economics, network queue position, deployed protocol/account compatibility, collateral settlement, real venue cancellation timing, AWS latency or sustained funded operation.

Before a funded canary, verify the intended eligible host and account, the supported deployed protocol/contract/collateral, balances/allowance, Telegram/HTTPS owner access, backup/restore and capacity alerts, fresh metadata and private-stream/heartbeat behavior. Keep authorization and small finite canary limits explicit. On-chain merge/redemption, sells, V3 and deposit-wallet EIP-1271 remain unsupported capabilities. Portfolio closeout and capital recycling are therefore material blockers to a full unattended 24-hour funded lifecycle; they are reported in `unsupported_operations` and cannot be inferred from read-only portfolio flags. Economic holdout remains separate from technical readiness.
