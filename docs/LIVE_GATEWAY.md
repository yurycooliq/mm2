# Live gateway: implemented technical scope

`mm2-live` is a BUY-only, single-account execution service with a real Polymarket SDK transport and an injectable offline transport. It does not establish strategy profitability, grant funded authorization, or establish deployed account acceptance. CLOB tests use an in-memory `Venue`; chain tests use local mock RPC servers and public fixture key `1`, with no actual account credentials or external money-moving calls.

The dependency is pinned to `polymarket_client_sdk_v2 = 0.7.0`. This implementation supports Polygon CLOB V2 token orders with EOA, canonical proxy, one-owner Safe and pinned native-beacon DepositWallet signature type 3. The SDK's type 3 order signature uses ERC7739/TypedDataSign, including the wallet domain and owner ECDSA signature; the controlling EOA remains the CLOB L2 authentication address. It rejects V3 positions, negative-risk markets, legacy UUPS DepositWallets and sells. Standard-market merge/redemption uses a separate direct or gasless Polygon worker. SDK support in this code must not be confused with acceptance of a particular account/market. A fresh venue protocol check is required before signing and during account reconciliation. See the [official Rust repository](https://github.com/Polymarket/rs-clob-client-v2), [pinned crate API](https://docs.rs/polymarket_client_sdk_v2/0.7.0/polymarket_client_sdk_v2/), and [official wallet authentication](https://docs.polymarket.com/trading/wallets-auth).

## Public integration interface

```rust
LiveRuntime::start(settings: LiveSettings, state_dir: PathBuf)
    -> Result<LiveHandle, String>; // async; production SDK transport
LiveRuntime::start_with_venue(settings, state_dir, Arc<dyn Venue>)
    -> Result<LiveHandle, String>; // async; dependency injection for offline tests

handle.snapshot() -> Arc<LiveSnapshot>;
handle.subscribe() -> watch::Receiver<Arc<LiveSnapshot>>;
handle.resume_ready() -> bool;
handle.try_submit_quotes(Vec<LiveQuote>, timestamp_ms: u64) -> Result<(), String>;
handle.command(command_id: String, ControlAction) -> Result<LiveControlReceipt, String>; // async
handle.shutdown() -> Result<(), String>; // async
```

`try_submit_quotes` replaces the entire desired set in one coalescing watch slot. It performs bounded local validation and does not wait for signing, HTTP, console polling or disk. Supply a fresh timestamp and keep refreshing the desired set while it remains wanted. Empty sets are accepted while paused. Signing/posting happen in the executor; a late preparation result is discarded if its desired identity or freshness no longer matches. This is not a lossless queue of individual strategy decisions.

Each quote carries `slot`, `condition_id`, `market_slug`, decimal `token_id`, `outcome`, exact `price_micros` and `quantity_micros`, `window_start_ms`, `window_end_ms`, `tick_micros`, `min_order_micros`, approved maximum `fee_bps`, `protocol` and `neg_risk`. Currency/shares use six decimal micro units; products use twelve decimal pico units serialized as strings. SDK size precision requires quantity multiples of 10,000 micro shares. The gateway resolves venue condition/token/outcome identity, accepting state, end time, minimum, tick and V2 fee parameters before it signs. It rejects mismatches rather than silently changing price, quantity, token or market.

Approved markets are bounded exact condition IDs and/or the explicitly configured `btc-updown-5m-` family. Family quotes require an integer slug timestamp aligned to five minutes, the matching start timestamp and a 300-second interval. The SDK then verifies the actual condition, token pair, slug and end time. The prefix does not authorize arbitrary caller-supplied tokens.

Owner actions are `Pause`, `Resume`, `Kill`, `Reset`. Commands have a bounded durable ID. Repeating an ID with a different action is a conflict. Repeating the same ID returns its stored receipt and does not reapply the action. In particular, a historical Resume receipt can say `running` while the current recovered executor remains paused. The caller must display current snapshot phase separately from receipt phase and use a new owner command to resume after recovery. The parent engine retains its own durable CAS command contract; child IDs preserve that identity across the two journals.

## Credentials, readiness and order preparation

`LiveSettings` contains public addresses, deployment identity, risk policy, scheduling bounds and environment-variable names. It never contains key values. `owner_authorized` defaults to false. Production startup validates the explicit account/funder/signer relationship and deployment configuration before it reads private environment values. EOA funder equals signer; proxy/Safe funders must match canonical SDK derivation. Type 3 requires a separate controlling signer, configured `[live.chain.relayer]`, and read-only onchain ownership/factory/beacon/domain checks. Supplied CLOB L2 credentials are used directly; no API key creation/derivation, allowance transaction or automatic funding occurs.

The inactive public templates identify account/funder `0x04Ad8Cb08F04b58fbcEa273603d6cd151Ba8aDB4` and controlling owner/signer `0xa2300f310b59df6d0dec94576776ce5435bd0b3f`. `owner_address` in the profile identifies the account under owner control; the wallet's onchain `owner()` is the signing address. Public RPC inspection establishes this relationship, not possession of its key or authenticated API acceptance. The EIP7702-delegated owner can still sign with its raw EOA key: the pinned wallet verifier tries ECDSA before contract-signature fallback.

For type 3, the owner creates a Relayer API key in Polymarket Settings → API Keys → Relayer API Keys. Its private environment references default to `MM2_POLY_RELAYER_API_KEY` and `MM2_POLY_RELAYER_API_KEY_ADDRESS`; the address must match the controlling signer/key owner. This key is distinct from the CLOB API key/secret/passphrase. Existing-account owner keys use the documented relayer route without a Builder account. Actual key eligibility, quota and selected-host authenticated access remain external acceptance checks. Keep all key values in private ignored runtime files; never send them through chat or telemetry. [Official existing-account and gasless setup](https://docs.polymarket.com/trading/wallets-auth)

Startup always recovers paused, preserving a killed latch. Active recovered orders become cancellation/reconciliation candidates. Readiness requires a connected authenticated user stream, a recent successful complete account reconciliation, heartbeat success, no foreign open order, no unresolved order outcome, and no fault. An owner Resume is rejected before these gates pass. Private stream disconnect durably pauses the executor and clears desired quotes; reconnect requires fresh reconciliation and a new Resume identity.

Preparation runs protocol, market and V2 token/fee metadata requests concurrently. Market and token metadata caches contain at most 64 entries each and expire after one second; a caller tick/minimum change bypasses the token cache. Immutable identity changes are rejected. The SDK's indefinitely cached `version()` is supplemented by a one-second public `/version` refresh using a pooled HTTPS client and compared with the signing client's version. An unsupported protocol is a visible preparation failure, not an automatic downgrade or version-changing resubmission.

V2 platform fees come from `/clob-markets/{condition}`'s `fd` parameters. Legacy V1 `fee_rate_bps` is not used. A taker-only fee is zero for these post-only maker orders. Otherwise the V2 price curve is converted upward to a conservative basis-point bound for reservation/accounting and must fit the caller's approved bound. The recorded gross purchase cost is conservative; it is not a confirmed settlement fee statement or PnL.

All orders are BUY and post-only. The SDK builds and signs GTC/GTD orders without submitting them. GTD is chosen where expiration satisfies its security buffer; the final minute uses GTC. This buffer is not a strategy-wide final-minute prohibition. Desired-quote expiration, source freshness and software cancellation still apply to GTC. The executor stops wanting orders one second before the configured market end; cancellation and fill delivery have finite network latency, so this does not prove that every order is terminal exactly at the deadline. The venue heartbeat provides an additional cancellation mechanism, and its actual selected-host behavior remains a canary gate.

## Durability, uncertainty and reservations

The signed V2 EIP-712 order hash is computed before any POST. Its validated quote, signed wire representation and possible-fill reservation are synchronously persisted before the network worker may submit. The SDK's combined build/sign/post helper is deliberately not used: it could rebuild an order identity on a protocol mismatch. A timeout or missing acknowledgement never causes a new submission of the same economic intent.

Post and cancel timeouts preserve `unknown_post`/`unknown_cancel` state and possible-fill reservations. Cancellation has dedicated worker capacity independent of a slow POST or preparation. A cancel acknowledgement only triggers an authoritative query; it does not release collateral. Recovery and runtime reconciliation use bounded open-order and trade pagination, per-order authenticated REST queries with at most eight concurrent active queries, balance/allowance and Data API position metadata. With closeout enabled, token quantities come from bounded Polygon reads at one canonical block. A generation barrier discards account passes started before a finalized closeout effect. A complete query pass is applied as one account observation; a non-404 error or identity mismatch discards partial results. A missing order/404 plus an empty open list is insufficient proof that a timed-out submission never reached the venue. Such uncertainty remains reserved and blocks Resume until it can be resolved. Authenticated websocket messages trigger REST reconciliation; they do not directly free funds.

Per-order cumulative fills are monotonic. Terminal fill regression and fills that contradict an already terminal observation fault the service. A separate persisted position floor captures pre-existing account holdings before new effects and increases only from owned cumulative fill deltas. Observed Data API quantity is compared with this floor; it is never used as the accumulator for later fill deltas. This handles both ahead and lagging portfolio snapshots without counting an owned fill twice, and the floor survives pruning of terminal diagnostics. Old live ledgers missing that floor are rejected rather than guessed. The session cash bound does not replenish from a stale balance response. Open orders belonging to another executor are shown as foreign identities and prevent resumption. This implementation does not adopt or automatically cancel foreign orders.

Before read-only preparation, an optimistic zero-fee risk check skips impossible slots so they cannot starve an admissible hedge. Read-only preparation then normalizes the venue maker fee before capital admission. The final normalized risk check remains before any durable send intent or external order, so a conservative caller fee bound cannot accidentally prevent a valid hedge solely before its authoritative maker fee has been learned.

The ledger preserves one finite capital pool across markets. Admission applies budget, gross exposure, maximum order/market counts, independent possible Up/Down fills and per-market imbalance. Opposite open orders do not cancel each other's worst-case inventory. `daily_loss_micros` is labelled `conservative_purchase_minus_confirmed_owned_returns_loss_bound`, and `pnl_available` is false. It charges purchases/fee estimates discovered today and credits only finalized returns attributable to today's owned quantities. Prior-day/imported holdings cannot reset this budget. Lifetime net purchase exposure and available cash credit only confirmed owned returns; stale balance responses and fresh deposits cannot replenish them. Changing the public risk configuration on restart does not erase historical spend or reservations.

## Persistence and bounded diagnostics

The account directory is fenced by `live.lock`. Trading and both profiles must point to the same explicit account `live_state_dir`; their separate parent/paper directories do not create a new funded-account budget. Files are `live-identity.json` and `live-{starting_sequence:016}.jsonl`. The identity file is raw SHA-256 hex of the serialized public tuple `(host, owner, funder, signer, signature_type, chain_id, protocol, exchange, collateral)`. Policy/env reference names are not part of that account/deployment identity.

Each newline record contains `sequence`, `previous_hash`, `hash`, `reason` and the full ledger. The hash covers the canonical serialized tuple `(sequence, previous_hash, reason, ledger)`. Replay validates sequence/hash continuity, canonical segment names, bounded lines and semantic quote/position quantities. A partial record is a startup error; it is not silently truncated. Only an empty final segment with the next starting sequence is accepted as a pre-write rotation crash state. Failed rotation/write/fsync poisons the writer until checked restart/replay. Reset cannot clear a persistence failure.

Segments rotate at 8 MiB, with at most 256 retained segments and a configurable total capacity from 1 MiB to 1 GiB. Records are limited to 1 MiB. Rotation preserves the full chain and never deletes old records. New posts stop before consuming the journal's reserved cancellation headroom; eventual total exhaustion faults execution and stops heartbeat renewal. This is finite storage, not automatic compaction or indefinite unattended operation. Use the repository's locked backup/restore tools and alert before capacity exhaustion; never delete unresolved intents or reset the account ledger to recover capacity.

Only proven terminal diagnostics older than the newest sixteen are removed from subsequent checkpoints; original audit records remain in retained segments. Zero floors are collected only when no retained order needs them. Positive inventory and active uncertainty are never evicted. Current records are full checkpoints, so storage/latency per state-changing event grows with the bounded retained ledger. Identical account reconciliation, stable desired quotes, time pulses and heartbeat updates do not produce checkpoint writes. Frequent fills, replacements, cancellation retries and owner commands still consume capacity; selected-host throughput/capacity must be measured. Limits include 256 tracked orders/signed intents, 128 positions, 2,048 control receipts, 256 private events, 32 owner commands and one desired-quote watch slot. These quotas fail closed.

`LiveSnapshot` exposes current phase/readiness, account/stream/heartbeat evidence timestamps, collateral, allowance, exact reserve, conservative available cash, positions, unknown/active orders and faults. Telemetry includes all active orders plus at most 16 closed diagnostics, with total tracked/active counts. It also exposes `journal_bytes`, `journal_max_bytes`, durable sequence, quote coalescing count, preparation attempts/failures and a bounded `last_prepare_error`. Signed wire intents and secrets are excluded. Signed execution journals remain private account material and must not be copied into browser/UI logs.

Periodic immutable snapshots are published at up to 4 Hz; control/network/fault transitions may publish immediately. Snapshot copying is bounded but has nonzero cost. JSON/percentile/history formatting belongs outside the execution actor. Console availability, SQLite and Telegram are not prerequisites for quote expiry, cancellation or reconciliation. `both` uses a separate paper actor, ledger and bounded feed/control mirroring; secondary delay/fault never waits on the live actor's decision path.

## Remaining activation and capability gates

Offline tests verify command/recovery identity, durability-before-effect, lost acknowledgements, partial fills, cancellation uncertainty, cancel priority, stale/disconnected streams, independent possible-fill limits, semantic replay validation, unchanged-checkpoint suppression and primary/paper isolation. They do not verify actual maker economics, network queue position, deployed protocol/account compatibility, collateral settlement, real venue cancellation timing, AWS latency or sustained funded operation.

Before a funded canary, verify the intended eligible host and account, supported protocol/contract/collateral, private CLOB/Relayer credential eligibility, balances/allowance, sole-writer approvals, Telegram/HTTPS owner access, backup/restore and capacity alerts, fresh metadata and private-stream/heartbeat behavior. Keep authorization and small finite canary limits explicit. Sells, V3 positions, negative-risk markets and legacy UUPS DepositWallets remain unsupported. Standard closeout and capital recycling are implemented locally; selected-account/RPC receipt acceptance and sustained funded operation require a canary. Read-only portfolio flags cannot establish resolution or credit cash. Economic holdout remains separate from technical readiness.


## Standard Polygon closeout

`[live.chain]` enables automatic closeout after a retained market window ends and every owned order for that condition is authoritatively terminal. The worker first considers mergeable pairs and rotates fairly between conditions so a delayed oracle cannot starve another market. One chain transaction may be pending per account. It has independent bounded worker capacity from CLOB preparation/cancellation; the current market continues under retained inventory/cash/gas caps.

`MM2_POLYGON_RPC_URL` names a private HTTPS RPC endpoint. Readiness checks Polygon 137, pinned exchange/CTF/pUSD/adapter getters, wallet ownership/control and ERC1155 approvals before Resume. Direct types 0/1/2 additionally require sufficient native signer POL under transaction/session gas caps. EOA calls the adapter; canonical proxy calls the pinned factory; one-owner Safe uses execTransaction with owner signature and a matching Safe success event. Outer status 1 plus ExecutionFailure is failure. Type 3 uses a gas sponsor and authenticated relayer nonce. No approval, key creation, deposit or funding transaction is implicit.

The public closeout adapter is `0xAdA100Db00Ca00073811820692005400218FcE1f`; pUSD is `0xC011a7E12a19f7B1f670d46F03B03f3342E82DFB`. The exchange outcome factory getter is independently pinned to `0xada100874d00e3331d00f2007a9c336a65009718`. Both adapter identities must resolve the same CTF/pUSD/underlying USDC.e deployment. CTF token IDs derive from USDCE and binary collection/index sets. Known token IDs must belong to that derived pair. Preparation canonicalizes CTF index order without assuming Up means index set 1. Redemption requires an authoritative payout denominator and per-leg integer arithmetic. See [official position management](https://docs.polymarket.com/trading/positions/manage) and [adapter source](https://github.com/Polymarket/ctf-exchange-v2/blob/main/src/adapters/CtfCollateralAdapter.sol).

Direct preparation reads/simulates/signs an exact EIP1559 envelope without broadcasting. The account actor syncs its full raw bytes, hash, nonce, wallet intent, prestate, payout and gas caps before eth_sendRawTransaction. Lost responses retain the original intent. Exact-byte rebroadcast while running is allowed; nonce increments, gas replacement and new economic intents are not invented. Paused recovery queries receipts and needs fresh Resume before direct rebroadcast. Missing receipt/nonce progression is not proof of absence.

Finality requires a canonical receipt block and finalized RPC block at the configured depth. Transaction-specific pinned pUSD transfers and CTF transfers from the funder to the adapter establish effects; independent market fills cannot be mistaken for proceeds. Redemption may also return existing adapter dust; this is recorded but never attributed to the bot's owned budget. Failed execution halts, records actual gas, credits no cash and needs owner investigation/Reset. Session gas plus the pending signed maximum must fit the POL cap; Reset never erases spend.

Receipt application atomically consumes inventory, preserves conservative remaining owned basis, records gas and credits only attributable owned payout. Imported holdings are consumed first and cannot create a fresh risk budget. Duplicate receipts cannot credit twice. UI exposes public receipt fields, pending hash, returned collateral, conservative realized result and bounded error; signed bytes stay private. Final net PnL is unavailable because fee costs are conservative and POL conversion is not invented.

Templates enable closeout with the publicly inspected DepositWallet/controller and retain `owner_authorized = false`. Setup requires the correct signature type, CTF closeout approval, pUSD/CTF exchange permissions, private credentials and HTTPS RPC supporting finalized/historical reads and bounded logs. Native POL applies to direct types 0/1/2. No funded canary or approval change occurred in preparing this package. Never change retained identity or discard its journal to force compatibility.

## Native-beacon DepositWallet closeout

Type 3 pins factory `0x00000000000Fb5C9ADea0298D729A0CB3823Cc07`, factory implementation `0x528cc05efac2b0d255e423272187efd41248abd7`, beacon `0x7A18EDfe055488A3128f01F563e5B479D92ffc3a`, and effective wallet implementation `0xf7f27C29e60fe6325beF8dA7F93250353d2e3294`. The beacon supports a per-wallet implementation pin, so preflight queries `implementation()` with `from = funder`. It also checks owner/pending owner, unpaused state, owner-derived wallet ID/predicted address, deployed code, wallet interface identity and EIP712 domain: `DepositWallet/1`, chain 137, wallet verifying contract, zero salt. Implementation/domain drift refuses execution. [Verified wallet/embedded beacon source](https://sourcify.dev/server/v2/contract/137/0xf7f27C29e60fe6325beF8dA7F93250353d2e3294?fields=all)

The owner signs a plain EIP712 `Batch(wallet,nonce,deadline,calls)` containing exactly one approved standard closeout call with native value zero. This differs from the nested ERC7739 CLOB order wrapper. The authenticated `/v1/account/transactions/params?address=<signer>&type=WALLET` nonce must equal the canonical wallet nonce before signing. The default deadline is 600 seconds, bounded to 60–3600. The factory's `proxy(Batch[],bytes[])` is operator-only; the relayer supplies its authorized operator. The owner does not need factory operator membership or POL gas for this route. [Official SDK batch signing](https://github.com/Polymarket/py-sdk/blob/main/src/polymarket/_internal/actions/relayer/signing/deposit_wallet.py)

The actor syncs the complete Batch digest, exact JSON envelope, signature, nonce, deadline, preparation block/prestate and payout metadata. It then syncs `dispatched = true` before exactly one POST to the pinned HTTPS `/submit`. Automatic HTTP retries, replacement signing and nonce refresh are disabled. A crash after that durable marker but before network dispatch remains conservative uncertainty; it is not silently resubmitted. A returned bounded request ID is recorded separately. The submit response does not supply a required onchain hash: later `/v1/account/transactions/<id>` gives a discovery hint. **The Batch digest is the pending intent identity; the receipt's transaction hash identifies a different relayer-paid blockchain transaction.** The two remain linked by `intent_hash`. Relayer API state or a failed outer transaction alone does not release inventory.

With an ID, lookup verifies its hinted transaction. With a lost acknowledgement, bounded `BatchExecuted(nonce)` log scanning starts from the pinned preparation block and continues with an ephemeral cursor; restart safely rescans. Defaults are 50 blocks/page and eight pages/lookup. Successful recovery requires canonical finalized receipt evidence, the full factory calldata containing exactly the authorized wallet batch/signature, one exact wallet Execution event followed by BatchExecuted, and the common CTF/pUSD effect checks. Sponsored gas is recorded separately and charges zero to the owner's POL budget. Missing or contradictory evidence retains uncertainty. [Relayer schema/signing implementation](https://github.com/Polymarket/py-sdk/blob/main/src/polymarket/_internal/actions/relayer/gasless.py)

Authorization expiry is a separate `RelayExpiry` proof: a canonical finalized timestamp strictly later than the signed deadline, unchanged wallet nonce and exact retained condition-token prestate. Unrelated collateral changes may be recorded but are not credited as proceeds. This proof can clear that expired pending authorization without inventing a transaction hash/receipt or payout. The actor enters a fault; the owner must investigate and Reset to paused before a fresh Resume. Changed nonce or condition holdings cannot use this expiry path and remain uncertain.

The sole-writer readiness/preparation gate rejects CTF approval for either external AutoRedeemer: `0xa1200000d0002264c9a1698e001292d00e1b00af` or `0xf3cfb6a6ebfeb51876289eb235719eb1c65252b0`. Public inspection found both capabilities approved on the configured account. Their operators can redeem whole binary positions without advancing wallet nonce, invalidating the bot's retained basis unless independently imported. The owner must disable these approvals through a separately authorized wallet operation before this implementation can Resume; reviewed external-receipt import is not implemented. Deploy/startup never revokes approvals or claims that this owner action occurred.
